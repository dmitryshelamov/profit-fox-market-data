# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/history-stream/spec.md`. Здесь только то, что определяет подход.

- Минутные свечи лежат в hypertable `candles`: чанки по дню UTC, сжатие через 7 дней, `segmentby instrument_id`,
  `orderby open_time`. Покрытие серии — multirange `candle_series.covered`, разобранный архивом buy volume — multirange
  `candle_series.settled`. Время до начала торгов покрыто без свечей и сразу разобрано. Свечи интервала REST собирает из минут
  через `time_bucket` (`GetCandlesQueries.Buckets`), по одному инструменту.
- У открытого интереса, соотношения лонг/шорт и выплат funding покрытие ряда — один отрезок `covered_from`/`covered_until`
  в `open_interest_series`, `long_short_ratio_series`, `funding_payment_series`.
- Потоковое чтение уже есть: `IStreamRequest` + `QueryUnbufferedAsync` (`GetClosedCandlesQueryHandler` и догон лент).
  `FeedCall` задаёт, как вызов ленты кончается с остановкой приложения.
- Состояние soyo-02 на 2026-11-17: 4 ядра, 14 ГБ памяти (7 свободно), Postgres `work_mem` 30 МБ,
  `max_parallel_workers_per_gather` 2; 1704 инструмента (929 linear, 521 spot, 254 акции), листингованы 1692; таблица свечей
  30 ГБ, сжатые 489 чанков — 1,7 ГБ; полный рынок в истории примерно с апреля 2026, загрузка до 1095 дней идёт. `settled`
  у всех листингованных Bybit доходит до начала текущего дня UTC; у акций T-Invest `settled` почти пуст (2 из 254), потому что
  их buy volume приходит со свечой.
- Замер на soyo-02, один сжатый день всего рынка (2,04 млн минут), одно ядро, без параллельных воркеров, во время загрузки
  истории:

  | Чтение | Время на день |
  |---|---|
  | `5m`, HashAggregate + сортировка время → инструмент, `work_mem` 30 МБ (хэш и сортировка уходят на диск) | 4,4 с |
  | то же, `work_mem` 256 МБ (хэш частью на диске, сортировка в памяти) | 3,8 с |
  | `5m` через GroupAggregate по инструменту | 19,4 с |
  | `1h` | 2,1 с |
  | `1m`, минуты в порядке время → инструмент | 1,8 с |

  Перенос на 1095 дней при нынешнем размере рынка: `5m` около часа на одном ядре, `1h`/`1d` около 40 минут. Основная цена —
  разжать минуты, свернуть их стоит 0,3–2,5 с на день.

## Goals / Non-Goals

**Goals:**

- Одна выборка на день окна и вид данных для всех инструментов запроса, а не по запросу на инструмент.
- Ни одного чтения, которое держит в памяти сервиса больше одного дня окна.
- Нагрузка одного чтения на базу — одно ядро; на все чтения — не больше `MaxConcurrentReads` ядер.

**Non-Goals:**

- Ускорять чтение агрегатами в базе: решение по замеру после деплоя, отдельным изменением.
- Снимок чтения одной транзакцией: повторяемость даёт окончательное покрытие, а не снимок базы.
- Отдавать текущий день, дозагружать с биржи, историю делистингованных пар.

## Decisions

### Контракт: метод `History` в каждой ленте, строка — живое сообщение

В `candle_feed.proto`, `open_interest_feed.proto`, `long_short_ratio_feed.proto`, `funding_payment_feed.proto` добавляется
`rpc History (<Kind>HistoryRequest) returns (stream <Kind>HistoryItem)`. Ответ — `oneof` из покрытия инструмента и строки,
строка — уже существующее сообщение ленты:

```proto
// candle_feed.proto
enum CandleInterval {
  CANDLE_INTERVAL_UNSPECIFIED = 0;
  CANDLE_INTERVAL_ONE_MINUTE = 1;
  CANDLE_INTERVAL_FIVE_MINUTES = 2;
  CANDLE_INTERVAL_FIFTEEN_MINUTES = 3;
  CANDLE_INTERVAL_ONE_HOUR = 4;
  CANDLE_INTERVAL_FOUR_HOURS = 5;
  CANDLE_INTERVAL_ONE_DAY = 6;
}

message CandleHistoryRequest {
  repeated string instrument_ids = 1;   // none means every listed instrument of the exchanges asked for
  repeated Exchange exchanges = 2;      // none means all
  google.protobuf.Timestamp from = 3;   // inclusive
  google.protobuf.Timestamp to = 4;     // exclusive, not after the start of the current UTC day
  CandleInterval interval = 5;
}

message CandleHistoryItem {
  oneof item {
    InstrumentCoverage coverage = 1;
    CandleUpdate candle = 2;
  }
}

// Shared by the History calls of every feed.
message InstrumentCoverage {
  string instrument_id = 1;
  repeated TimeRange ranges = 2;
}

message TimeRange {
  google.protobuf.Timestamp from = 1;   // inclusive
  google.protobuf.Timestamp until = 2;  // exclusive
}
```

Запросы трёх точечных лент — те же поля без `interval` (`OpenInterestHistoryRequest`, `LongShortRatioHistoryRequest`,
`FundingPaymentHistoryRequest`), ответы — `OpenInterestHistoryItem` с `OpenInterestUpdate point`, и так далее.

- Почему в лентах, а не отдельный сервис истории: бэктест и лайв бота разбирают одно сообщение, а правило от 2026-11-15
  прямо говорит, что метод истории добавляется в ленту, когда потребителю мало страниц. Отдельный `MarketHistory` дал бы один
  файл для копирования, но развёл бы историю и лайв по типам.
- `Exchange`, `InstrumentCoverage` и `TimeRange` объявлены в `candle_feed.proto`; три точечных контракта импортируют его.
  Это отступление от «контракт сам по себе»: свои копии покрытия в каждом файле означали бы четыре одинаковых сообщения под
  разными именами. Потребитель истории и так копирует `candle_feed.proto` первым.
- Почему покрытие сообщениями в начале потока, а не в заголовках ответа: для всего рынка это ~1700 сообщений, заголовки
  HTTP/2 для такого не годятся; а трейлеры приходят после строк, когда потребитель уже прочитал неполные данные.
- Пакет остаётся `profitfox.marketdata.v1`: всё только добавляется. `SubscribeRequest` и сообщения лент не меняются.

### Два запроса: покрытие, затем строки внутри него

Каждый вид данных — два запроса Application:

1. `Get<Kind>HistoryCoverageQuery` (`IRequest`) — инструменты запроса и их окончательное покрытие, обрезанное по окну,
   в порядке `instrument_id`. Целиком в памяти: ~1700 строк.
2. `Get<Kind>HistoryQuery` (`IStreamRequest`) — строки только внутри покрытия, которое ему передали.

Вызов gRPC сначала отправляет покрытие, затем строки. Требование «строки только внутри прочитанного покрытия» выполняется тем,
что второй запрос не знает другого покрытия: минуты, загруженные между двумя запросами, в ответ не попадают.

- Почему не один поток с объединением типов: в C# нет размеченного объединения, а базовый тип для двух записей смешал бы
  контракты Application ради одного вызова.
- Почему не одна транзакция `REPEATABLE READ` на всё чтение: она держала бы снимок базы до часа, мешая vacuum и сжатию
  чанков, пока идёт загрузка истории. Окончательное покрытие не меняется, поэтому снимок не нужен.

Окна — в `Queries`: `HistoryWindow` (`from` < `to` ≤ начала текущего дня UTC по `TimeProvider`) общее для точечных видов,
`CandleHistoryWindow` добавляет интервал и выравнивание. Нарушение — `ArgumentException`, как у `CandleWindow` и `PointWindow`;
вызов истории переводит его в `INVALID_ARGUMENT`, `InstrumentNotFoundException` — в `NOT_FOUND`.

### Окончательное покрытие свечей считается в SQL

Обработчик покрытия свечей одним запросом берёт листингованные инструменты запроса (фильтр по `id` и биржам, `delisted_at IS
NULL`) с их серией: у Bybit `covered * settled`, у T-Invest `covered` (биржу даёт наличие строки в `bybit_listings` /
`tinvest_shares`), затем `* tstzmultirange(tstzrange(@From, @To))`, `ORDER BY instrument_id`. Названные `id`, которых нет в
каталоге, дают `InstrumentNotFoundException` до чтения строк. Точечные виды так же берут `[covered_from, covered_until)` ряда.

- Почему пересечение с `settled` только у Bybit: у T-Invest архива нет, `settled` у акций почти пуст, и пересечение оставило
  бы их без истории.

### Строки читаются по дню UTC одной выборкой на все инструменты

Обработчик строк идёт по дням UTC окна, в которых покрытие хоть одного инструмента не пусто, и на каждый день делает одну
выборку `QueryUnbufferedAsync` по всем инструментам запроса. Покрытие передаётся массивами `@InstrumentIds::uuid[]` и
`@Ranges::tstzmultirange[]` и соединяется через `unnest`:

- минуты: `WHERE cov.ranges @> c.open_time`, `ORDER BY c.open_time, c.instrument_id`;
- интервалы: тот же `time_bucket` и те же агрегаты, что в `GetCandlesQueries.Buckets`, группировка по инструменту и началу
  свечи, `HAVING cov.ranges @> tstzrange(bucket, bucket + interval)`, `ORDER BY bucket, instrument_id`. Все интервалы делят
  сутки нацело, поэтому свеча не пересекает границу дня выборки;
- точки: `WHERE cov.ranges @> p.time`, `ORDER BY p.time, p.instrument_id`.

- Почему по дню: чанк `candles` — день, и Postgres сортирует только день (≤ 2 млн минут, ~400 тыс. свечей `5m`), а память
  .NET — одна строка. Окно целиком одной выборкой требовало бы сортировки всего окна в базе.
- Почему HashAggregate, а не GroupAggregate по инструменту: замер — 3,8–4,4 с против 19,4 с на день; порядок время →
  инструмент выходит из одной сортировки после хэша.
- Почему порядок `instrument_id` из Postgres: его сравнение `uuid` побайтовое и не меняется между чтениями; `Guid` в .NET
  сравнивается иначе, поэтому потребитель не пересортировывает.
- Точечные виды идут по тем же дням: выплат мало, но одна схема чтения на четыре вида проще, а 1095 маленьких выборок — секунды.

Соединение — scoped `NpgsqlConnection` вызова. Перед первой выборкой на нём выполняется `SET max_parallel_workers_per_gather =
0` и `SET work_mem = '256MB'`: одно ядро на чтение и хэш без лишнего выхода на диск. Npgsql сбрасывает состояние сессии при
возврате соединения в пул, поэтому настройки не уходят к другим запросам. Это константы обработчиков, не настройки: менять их
без замера незачем.

### Очередь чтений: семафор в Presentation

`HistoryCall` в `GrpcServices` (по образцу `FeedCall`) делает то, что одинаково у четырёх `History`: ждёт место в очереди,
читает покрытие и отправляет его, затем строки; переводит исключения в коды; связывает отмену с `ApplicationStopping`, чтобы
идущие и ожидающие вызовы кончались с `UNAVAILABLE`. Очередь — singleton `HistoryReadGate`: счётчик занятых мест и очередь
ожидающих, предел читается из `IOptionsMonitor<HistoryReadSettings>` (секция `HistoryRead`, `MaxConcurrentReads` = 2) при каждом
вызове. Новый предел действует с ближайшего освобождения места; уже идущие чтения не прерываются. `HistoryReadSettings` — в
`Presentation/Settings`, с `Validate` (> 0) и `ValidateOnStart`, как `CandleFeedSettings`.

- Почему ждать, а не отказывать с `RESOURCE_EXHAUSTED`: потребители свои, стенд может запустить несколько периодов, и повтор
  после отказа был бы его заботой без пользы. Ожидание ограничено отменой и deadline потребителя.
- Почему таймаута простоя нет: HTTP/2 сам останавливает запись, когда потребитель не читает, память не растёт; зависший
  потребитель держит место, пока не оборвёт вызов. Если это станет мешать, таймаут добавится отдельно.

### Значения и повторяемость

Минуты и точки идут текстом из `decimal`, как в живых лентах: Npgsql сохраняет масштаб `numeric`, текст повторяет хранилище.
Свечи интервала считаются той же SQL, что и в REST, поэтому одинаковые минуты дают одинаковые суммы и оценку оборота T-Invest.
Комментарий контракта `History` говорит потребителю: хэшировать разобранные поля в порядке прихода, а не байты protobuf;
история — только листингованные сейчас инструменты (survivorship bias); покрытие свечей Bybit кончается там, где кончается
разобранный архивом день.

## Risks / Trade-offs

- [Чтение рынка за 3 года по `5m` — около часа] → принято на старте; после деплоя замер на soyo-02, агрегаты — отдельным изменением.
- [Два чтения одновременно занимают два ядра из четырёх, пока идёт загрузка истории] → предел меняется без перезапуска; замер
  покажет, мешает ли загрузке.
- [Медленный потребитель держит открытую выборку дня, то есть снимок базы, пока не дочитает день] → один день, а не всё окно;
  чтения ограничены `MaxConcurrentReads`.
- [`work_mem` 256 МБ на чтение] → не больше 0,5 ГБ на два чтения при 7 ГБ свободных; хэш одного дня `5m` — ~170 МБ.
- [Пары, делистингованные после запуска сервиса, пропадают и из прошлых периодов] → сознательное решение владельца; контракт
  говорит об этом потребителю.
- [Оценка оборота T-Invest делением `numeric` может дать больше знаков, чем вмещает `decimal`] → та же SQL уже работает в REST;
  если чтение упадёт на этом, ограничить масштаб в SQL одинаково для REST и истории.
- [Три точечных контракта зависят от `candle_feed.proto`] → потребитель копирует два файла вместо одного.

## Migration Plan

Схема не меняется. Деплой — обычный `vN` по слову владельца; подписчики `Subscribe` не затрагиваются, потребители истории
копируют обновлённые `.proto`. Откат — предыдущий образ: новые методы просто исчезают.
