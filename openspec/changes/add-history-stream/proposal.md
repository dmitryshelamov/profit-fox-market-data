# Proposal

## Why

Стенд гипотез и бэктест бота будут читать историю прямо из market-data, без своего снимка. Сейчас история отдаётся только
запросами REST по одному инструменту и не больше 1000 строк за раз, а свечи перед чтением ещё и догружаются с биржи. Чтобы
прочитать рынок за период, потребитель делал бы тысячи запросов, и повторное чтение того же окна могло бы вернуть другое.
Нужно одно чтение потоком за весь рынок и окно, без лимита, только из того, что уже окончательно лежит в хранилище, и с
одинаковым ответом при повторе. Это изменение идёт первым: на нём строится сквозной кусок Engine + Bench на гипотезе H0001.

## What Changes

- В ленты `CandleFeed`, `OpenInterestFeed`, `LongShortRatioFeed`, `FundingPaymentFeed` добавляется по методу gRPC
  server-streaming `History`: набор инструментов или весь рынок, окно `[from, to)`, у свечей интервал `1m`/`5m`/`15m`/`1h`/`4h`/`1d`.
- Ответ сначала сообщает покрытие окна по каждому инструменту, затем отдаёт строки в порядке время → инструмент. Строки берутся
  только из окончательного покрытия: для свечей Bybit — загруженные минуты, у которых buy volume уже разобран архивом
  (`covered ∩ settled`); для T-Invest и точечных рядов — их покрытие.
- Строка истории — то же сообщение, что идёт в ленте вживую (`CandleUpdate`, `OpenInterestUpdate`, `LongShortRatioUpdate`,
  `FundingPaymentUpdate`), чтобы бэктест и лайв разбирали одно и то же.
- С биржи при чтении ничего не загружается. Окно должно кончаться не позже начала текущего дня UTC: история — только прошедшие дни.
- Отдаются только листингованные инструменты; делистингованные пропускаются, даже если их запросили явно.
- Чтение дешёвое для soyo-02: не больше `HistoryRead:MaxConcurrentReads` чтений одновременно (по умолчанию 2), каждое на одном
  ядре Postgres и по одному дню UTC за запрос к базе, строки идут по мере чтения. Лимита на длину окна и число строк нет.
- Без авторизации, в прежнем пакете `profitfox.marketdata.v1`: методы и сообщения только добавляются, подписчики `Subscribe`
  ничего не замечают.

Не входят: прогнозная ставка funding (у неё нет покрытия), ликвидации (их не просил потребитель), время листинга в каталоге,
история делистингованных пар, агрегаты интервалов в базе (continuous aggregates) — отдельным изменением, если чтения при замере
окажутся слишком долгими. REST-запросы истории остаются как есть.

## Capabilities

### New Capabilities

- `history-stream`: чтение окончательной истории свечей, открытого интереса, соотношения лонг/шорт и выплат funding потоком
  gRPC за набор инструментов или весь рынок: покрытие окна, порядок и повторяемость ответа, допустимые окна, ограничение
  нагрузки на хранилище.

## Impact

- Контракты `Protos/candle_feed.proto`, `open_interest_feed.proto`, `long_short_ratio_feed.proto`, `funding_payment_feed.proto`:
  новые методы `History`, их запросы и сообщения ответа, общие для потоков истории сообщения покрытия. Потребители копируют
  обновлённые `.proto`.
- Presentation: методы `History` в `CandleFeedService`, `OpenInterestFeedService`, `LongShortRatioFeedService`,
  `FundingPaymentFeedService` и общее для них устройство вызова истории (по образцу `FeedCall`).
- Application: потоковые запросы истории (`IStreamRequest`) четырёх видов и их окна в `Queries/<Area>`.
- Infrastructure: обработчики запросов истории с SQL в `Persistence/Queries/Handlers/<Area>`, ограничение одновременных чтений,
  настройки `HistoryRead` в `appsettings.json`.
- Хранилище: схема и миграции не меняются; добавляются только чтения.
- `docs/conventions.md`: правило «история — REST по инструменту, пока потребителю хватает страниц» дополняется методами `History`.
- soyo-02: после деплоя — замер чтения рынка за период, чтобы решить, нужны ли агрегаты.
